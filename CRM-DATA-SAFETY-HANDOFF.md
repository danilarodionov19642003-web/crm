# Проверка CRM для одновременной работы без потери данных

> Актуальный эталон Mentori CRM на 26.07.2026, commit `03595cb`.
> Документ предназначен для передачи в другую Codex-сессию. Он описывает
> фактическую защиту текущей CRM, ее ограничения и обязательный порядок аудита
> другой CRM, в которой два человека могут одновременно работать под одним входом.

## 1. Готовое задание для другой сессии

Передай этой сессии данный файл и следующий запрос:

```text
Изучи приложенный CRM-DATA-SAFETY-HANDOFF.md и фактический код этой CRM.

Нужно проверить абсолютно все пути чтения и записи данных: браузерные формы,
автосохранение, API, серверные обработчики, боты, фоновые задачи, импорты,
платежные webhook, личные кабинеты, загрузки файлов, триггеры БД и ручные
админские операции. Два человека могут одновременно работать под одним логином,
в разных браузерах и вкладках.

Сначала ничего не меняй в продовых данных. Составь карту источников записи и
определи реальную модель хранения. Не доверяй README без проверки кода, схемы БД
и работающего окружения.

Перед любыми исправлениями:
1. сделай полный бэкап БД и отдельно экспорт критических таблиц;
2. проверь, что бэкап читается и может быть восстановлен в тестовую БД;
3. зафиксируй исходные количества строк и ключевые контрольные суммы;
4. не добавляй бэкапы, дампы, .env и секреты в Git.

Сравни реализацию с требованиями этого документа. Найденные безопасные кодовые
исправления внеси, добавь автоматические тесты конкурентности и проверь их.
Продовые миграции и переключения выполняй только после проверенного бэкапа,
с обратимым планом и контрольной проверкой данных после операции.

Главный критерий: ни один неуспешный запрос, старая вкладка, параллельный
пользователь, бот, webhook, повторный клик, обрыв сети или перезагрузка страницы
не должны молча удалить либо откатить уже подтвержденные данные.

В конце дай вердикт по каждой гипотезе, список всех найденных writers, перечень
исправлений, результаты двухбраузерного теста и точную инструкцию отката.
```

## 2. Главный принцип сравнения

Не надо механически копировать Mentori CRM. Ее текущая защита надежнее прежней,
но основное состояние все еще хранится одним JSON-документом. Для новой CRM
предпочтительна нормализованная схема: одна сущность или операция = одна строка.

Сравнивать нужно не названия функций, а инварианты:

1. Подтвержденная сервером запись не может исчезнуть из-за старой вкладки.
2. Неотправленная локальная правка не пропадает после reload или обрыва сети.
3. Конфликт обнаруживается атомарно на сервере, а не только предварительным GET.
4. Все автоматические writers используют тот же безопасный контракт.
5. Повтор операции не создает дубль.
6. Многошаговая денежная операция либо завершается целиком, либо не применяется.
7. Есть независимые бэкапы и доказанная процедура восстановления.
8. Можно установить, кто, когда и что изменил.

## 3. Что фактически хранит Mentori CRM

Основной админский state хранится в Postgres:

```text
public.crm_state
  id = 'main'
  data = один JSONB со всей CRM
  updated_at = версия документа для optimistic locking
```

Связанные контуры вынесены отдельно:

| Контур | Источник истины | Назначение |
|---|---|---|
| Админская CRM | `crm_state` | Клиенты, аккаунты, статусы, финансы и настройки |
| История state | `crm_state_history` | До 500 полных снимков для отката |
| Кабинеты клиентов | `client_snapshots` | Персональный read-model по email, без внутренних данных CRM |
| Заказы клиентов | `client_orders` | Отдельные заявки, чеки, согласия и статусы |
| Онлайн-оплаты | `payment_transactions` | Идемпотентный журнал платежей провайдера |
| Webhook оплаты | `payment_webhook_events` | Дедупликация и аудит входящих событий |
| Telegram | `notification_outbox` | Очередь уведомлений, отделенная от основного state |
| Чеки | Private Storage bucket `receipts` | Файлы чеков, в заказе хранится внутренний reference |

Клиентские кабинеты не читают `crm_state`. Они читают только собственную строку
`client_snapshots` и собственные строки `client_orders`, что ограничивается RLS.

## 4. Как браузер Mentori CRM сохраняет изменение

Фактический путь находится в `js/app.js` и `js/cloud-sync.js`.

### 4.1 Локальный клик Save

1. `Store.save()` сериализует текущий state в `localStorage`.
2. `CloudSync.push(state)` создает глубокую копию состояния. Живая ссылка на
   мутирующий `Store.state` в сетевой запрос не передается.
3. При первом изменении фиксируются:
   - `pendingState`: локальная версия с правкой;
   - `pendingBase`: подтвержденный серверный снимок, от которого сделана правка;
   - `pendingBaseUpdatedAt`: версия этого снимка.
4. Вся тройка сразу записывается в `localStorage` как durable pending.
5. Несколько быстрых Save объединяются debounce-паузой `600 мс`, но база merge
   остается исходной, поэтому промежуточные правки не выпадают.

### 4.2 Запись на сервер

1. До первого успешного pull любой push заблокирован. Это не позволяет пустому
   стартовому state обогнать загрузку боевых данных.
2. Перед push вкладка читает текущий серверный state и его `updated_at`.
3. Если сервер изменился, выполняется трехсторонний merge:

```text
base   = версия, от которой пользователь начал менять данные
local  = несохраненная правка пользователя
remote = последняя версия сервера
result = merge(base, local, remote)
```

4. Итог записывается условным PATCH:

```text
UPDATE crm_state
SET data = result, updated_at = new_version
WHERE id = 'main' AND updated_at = expected_version
```

5. Если обновлено `0 rows`, другая запись успела между GET и PATCH. Это CAS
   conflict: pending не удаляется, через `250 мс` процесс заново читает сервер,
   объединяет версии и повторяет условную запись.
6. Сетевые ошибки повторяются с паузами `5с -> 15с -> 45с -> 2м -> 5м`.
7. Pending очищается только после подтвержденного успешного CAS.

Предварительный GET сам по себе не является защитой. Критическая защита именно
в условном UPDATE/PATCH, который атомарно проверяет версию внутри БД.

### 4.3 Изменение во время уже отправленного запроса

`pendingRevision` отмечает каждый новый локальный снимок. Если пользователь
снова нажал Save, пока первый PATCH находится в сети, первая успешная запись не
очищает более свежий pending. Новая правка перебазируется на только что записанный
state и отправляется следующим guarded PATCH.

### 4.4 Pull, возврат во вкладку и восстановление связи

- Видимая вкладка делает pull раз в `60 секунд`.
- При `online`, `pageshow` и возврате из hidden выполняются pull, затем flush.
- Pull и push сериализованы внутри одной вкладки через единый `flushPromise`.
- Если есть pending, pull не заменяет его серверным снимком. Он сначала делает
  merge, показывает объединенный state и ставит его на безопасную отправку.
- При закрытии или сворачивании нет безусловного keepalive-PATCH. Вкладка только
  гарантированно оставляет pending локально; replay выполняется после следующего
  запуска с проверкой версии.

## 5. Правила трехстороннего merge в текущей CRM

| Сценарий | Результат |
|---|---|
| Изменены разные записи | Сохраняются обе правки |
| Изменены разные поля одной записи | Сохраняются оба поля |
| Изменено одно скалярное поле | Побеждает более поздний pending Save; конфликт протоколируется |
| Одна сторона удаляет, другая редактирует | Редактируемая запись сохраняется |
| Массив объектов со стабильным `id` | Merge по `id` |
| `schedule` без `id` | Merge по `date` |
| `items` без `id` | Merge по `accountId` |
| Append-only история | Новые элементы обеих сторон добавляются |
| Массив уникальных примитивов | Объединяются добавления и удаления |
| Структурный массив без стабильного ключа | Локальный вариант, запись в conflict log |

При настоящем same-field конфликте физически нельзя оставить в одном поле два
разных значения. Поэтому текущая CRM:

1. применяет более поздний локальный Save;
2. сохраняет предыдущий полный remote-снимок в локальный conflict backup;
3. запускает принудительную best-effort запись предыдущего remote-снимка в
   серверную историю;
4. записывает путь поля, base/local/remote и выбранное решение в conflict log;
5. показывает пользователю уведомление об объединении.

## 6. Локальная страховка браузера

Используются следующие ключи `localStorage`:

| Ключ | Содержимое |
|---|---|
| `mentori-crm-v2` | Текущая локальная рабочая копия |
| `mentori-crm-meta` | Последние подтвержденные версии pull/push |
| `mentori-crm-pending` | Несохраненный state + base + base version |
| `mentori-crm-pending-quarantine` | Старый/неполный pending, который опасно replay-ить |
| `mentori-crm-sync-conflicts` | Последние 20 описаний конфликтов |
| `mentori-crm-sync-conflict-backup` | Последний полный remote до разрешения конфликта |

Pending без `base` или `baseUpdatedAt` никогда не отправляется поверх сервера.
Он переносится в quarantine. Это исправляет старый сценарий, когда вчерашний
локальный снимок после открытия CRM откатывал свежую работу другого человека.

Важно: `localStorage` защищает только от reload/закрытия на том же устройстве.
Потеря устройства или очистка браузера до отправки уничтожит локальный pending.
Это не замена серверному draft/audit log.

## 7. Защита остальных writers

### 7.1 Telegram-бот и AKIRA

Бот не делает прямой безусловный upsert. Контролируемые операции находятся в
`/Users/mentori/tg/backend/routers/meta.py`:

```text
read data + updated_at
-> validate required collections
-> save pre-change history snapshot
-> append exactly one business operation
-> PATCH WHERE updated_at = expected
-> conflict means refusal, not overwrite
```

При конфликте endpoint возвращает `ok=false` и просит повторить операцию. Кроме
того, браузер перед своим push подмешивает отсутствующие bot-origin записи
`income` и `expenses`, чтобы устаревшая вкладка не стерла только что добавленную
ботом финансовую операцию.

Обычные Telegram-уведомления работают через `notification_outbox`. Notifier
читает очередь и не меняет `crm_state`.

### 7.2 Клиентские заказы и чеки

Кабинет клиента создает отдельную строку `client_orders` под JWT клиента. RLS
проверяет совпадение email и запрещает клиенту самостоятельно поставить статус
`confirmed` или платежные поля. Чек загружается без upsert в папку `auth.uid()`,
а в заказе сохраняется private reference. Для просмотра Storage выдаёт
авторизованному пользователю временную signed URL на пять минут.

Заявка является отдельной записью, а не изменением общего browser state. Это
намного безопаснее для конкурентной работы и является правильным образцом для
новой CRM.

### 7.3 Онлайн-оплата и ручное подтверждение перевода

Payment backend выполняет бизнес-применение в одной SQL-транзакции:

1. блокирует `payment_transactions`/`client_orders` через `FOR UPDATE`;
2. проверяет сумму, валюту, статус и принадлежность заказа;
3. блокирует строку `crm_state` через `FOR UPDATE`;
4. идемпотентно применяет заказ и финансовую операцию;
5. обновляет order, payment transaction и client snapshot;
6. добавляет уведомление в outbox;
7. фиксирует `business_applied_at`, чтобы повторный webhook ничего не начислил.

Уникальные provider IDs и журнал webhook защищают от повторной доставки события.
Обновление `crm_state.updated_at` заставляет открытую старую вкладку обнаружить
эту серверную операцию через CAS и выполнить merge.

## 8. Слои резервирования Mentori CRM

### 8.1 Что есть сейчас

1. `crm_state_history`: максимум 500 полных снимков. В каждом экземпляре вкладки
   обычные browser snapshots запускаются не чаще раза в 5 минут; при same-field
   конфликте remote-снимок отправляется в историю вне этого throttle. История
   является best-effort и не блокирует основной Save. На момент проверки таблица
   содержит 500 строк.
2. Бот перед контролируемой записью делает pre-change history snapshot.
3. Кнопка в шапке скачивает актуальный серверный state как JSON. Если сервер
   недоступен, файл явно помечается `LOCAL` и содержит локальную копию.
4. Перед последним sync-релизом созданы полный `pg_dump` и отдельный JSON state.
5. Код хранится в Git, но Git не является бэкапом пользовательских данных.
6. На Beget включён `mentori-db-backup.timer`: ночью около 03:20 МСК он создаёт
   custom-format `pg_dump`, globals ролей, проверяет каталог через `pg_restore`
   и пишет SHA-256. Локальная ротация — 30 дней; скрипт лежит в `ops/backup/`.
7. Контрольная копия дампа от 26.07.2026 скачана на рабочий Mac в игнорируемую
   Git папку `backups/server-daily/` и повторно проверена по SHA-256.

### 8.2 Чего сейчас недостаточно

Автоматическая копия пока хранится на production-сервере. Это защищает от
ошибочного изменения и неудачной миграции, но не от потери всего сервера или
диска. Нужна ежедневная зашифрованная отправка второго экземпляра в независимое
хранилище; снапшоты хостинг-провайдера этой проверкой не подтверждены.

`crm_state_history` и ежедневные server dumps находятся на том же сервере. Они
спасают от логической ошибки, но не от полной потери сервера. Payment backend хранит
транзакционный аудит платежа, но перед прямым обновлением `crm_state` не создает
отдельный полный history snapshot.

### 8.3 Обязательный стандарт для другой CRM

- PITR/WAL или эквивалентный point-in-time recovery.
- Ежедневный `pg_dump` по расписанию.
- Копия дампа в другом физическом месте, не только на сервере БД.
- Ротация минимум: 7 дневных, 4 недельных, 6 месячных.
- Бэкап перед каждой миграцией и опасным массовым изменением.
- Ежемесячный тест восстановления в пустую тестовую БД.
- Контроль количества строк, FK и выборочных business totals после restore.
- Алерт, если очередной бэкап не создан или имеет подозрительный размер.
- `backups/`, `*.dump`, `*.bak`, `.env` и файлы секретов исключены из Git.

## 9. Честные ограничения текущей модели

1. Один JSONB остается общей точкой конфликта. CAS + merge защищают от тихого
   overwrite, но код сложнее и требует поддержки правил для каждой структуры.
2. Два одновременных разных значения одного поля нельзя автоматически признать
   оба правильными. Одно применяется, второе остается в истории/журнале.
3. Вкладки получают изменения не realtime, а при возврате или периодическом pull.
   Сохранение все равно безопасно благодаря preflight + CAS.
4. `client_snapshots` после обычного browser Save обновляются best-effort и могут
   временно отстать. Источник истины должен оставаться в основных таблицах.
5. Общий логин не позволяет доказательно определить человека по JWT. Если нужны
   авторство и зарплата, нужны отдельные аккаунты. Минимальный компромисс при
   общем входе: обязательный выбранный `actor_id` на устройстве и запись его в
   каждое изменение, но это слабее отдельных учетных записей.
6. История и локальный pending дополняют, но не заменяют внешний полный бэкап.

## 10. Какой вариант должен предпочесть другая CRM

### Вариант A: данные уже разложены по таблицам

Это предпочтительный случай. Не внедрять общий JSON и ручной global merge.

- Каждая сущность имеет `id`, `version`, `created_at`, `updated_at`,
  `created_by`, `updated_by`, `deleted_at`.
- UI отправляет PATCH только измененной строки/поля.
- UPDATE выполняется с `WHERE id=? AND version=?` и увеличивает `version`.
- `0 rows affected` возвращается как `409 Conflict`, правка остается pending.
- Создающие операции имеют уникальный `idempotency_key`.
- Удаление по умолчанию soft-delete.
- Audit log фиксирует old/new, actor и время на уровне БД.
- Realtime/SSE/WebSocket обновляет открытые экраны, но не заменяет version check.

Эталон условного обновления:

```sql
update clients
set name = $1,
    version = version + 1,
    updated_at = now(),
    updated_by = $2
where id = $3 and version = $4
returning *;
```

### Вариант B: CRM тоже хранит один document/blob

До нормализации обязательны все элементы:

```text
confirmed base snapshot
+ immutable local pending
+ persisted merge base and exact version
+ initial pull barrier
+ three-way merge
+ atomic CAS write
+ retry without clearing pending
+ in-flight rebase
+ conflict log and pre-conflict backup
+ empty-over-nonempty block
+ safe handling of hidden/offline/reload
+ identical contract for every bot/webhook/backend writer
```

Без хотя бы одного из этих пунктов нельзя утверждать, что два человека под одним
входом не будут затирать друг друга.

## 11. Обязательная карта writers для аудита

Сессия должна найти не только очевидный `save()`:

- все `INSERT`, `UPDATE`, `DELETE`, `UPSERT`, ORM `.save()`/`.update()`;
- REST `POST`, `PATCH`, `PUT`, RPC и GraphQL mutations;
- localStorage/IndexedDB queues и service workers;
- autosave, debounce, unload/pagehide/visibility handlers;
- Telegram/WhatsApp/почтовые боты;
- cron, Celery, queues, n8n и другие automation workflows;
- платежные callback/webhook и ручное подтверждение;
- импорты CSV/XLSX и массовые операции;
- SQL functions, triggers и `SECURITY DEFINER`;
- админские скрипты, миграции и repair-команды;
- клиентские кабинеты и mobile-приложения;
- зеркала/read-models, которые могут ошибочно считаться источником истины.

Для каждого writer зафиксировать:

| Поле | Что проверить |
|---|---|
| Кто вызывает | Пользователь, бот, webhook, cron, админ |
| Что читает | Строка, документ, версия |
| Что пишет | Поле, строка, весь state |
| Проверка конфликта | CAS/version/row lock или отсутствует |
| Retry | Идемпотентен ли повтор |
| Audit | Где old/new и actor |
| Recovery | Что остается после ошибки посередине |
| Права | Какая DB role/RLS policy |

Красные флаги:

- безусловный upsert всего документа;
- `updated_at` проверяется только клиентским `if`, но не в SQL WHERE;
- pending очищается до ответа сервера;
- при ошибке выполняется pull, который заменяет локальную правку;
- hidden/unload отправляет отдельный незащищенный запрос;
- повтор webhook снова начисляет деньги;
- client snapshot используется как единственная финансовая правда;
- тесты меняют реальные данные или реальные выплаты;
- бэкап лежит только рядом с продовой БД;
- один JWT используется как доказательство, кто из двух сотрудников внес правку.

## 12. Обязательная тест-матрица

Проверять минимум в двух независимых browser contexts с общей тестовой БД или
изолированной тестовой записью. После каждого сценария сравнивать сервер, UI,
историю и pending.

| N | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Два пользователя меняют разные записи | Обе правки сохранены |
| 2 | Два пользователя меняют разные поля одной записи | Оба поля сохранены |
| 3 | Два пользователя меняют одно поле | Явный конфликт; проигравшее значение восстановимо |
| 4 | Один удаляет, другой редактирует | Нет тихого уничтожения записи |
| 5 | Второй Save во время первого запроса | Второй Save остается в очереди и доходит |
| 6 | Чужая запись между GET и PATCH | CAS отклоняет старый PATCH, затем merge/retry |
| 7 | Save сразу после открытия, до первого pull | Сервер не затирается, локальная правка сохраняется |
| 8 | Reload с pending | Pending merge-ится с сервером и очищается только после успеха |
| 9 | Старый pending без base/version | Quarantine, никакого автоматического overwrite |
| 10 | Работа offline, затем online | Правки досылаются без потери свежего remote |
| 11 | Вкладка скрыта сутки, затем Save | Вчерашний state не затирает сегодняшнюю работу |
| 12 | Бот пишет во время открытой старой вкладки | Обе операции сохраняются |
| 13 | Webhook приходит дважды | Бизнес-операция применяется один раз |
| 14 | Сервер падает между шагами платежа | Нет частично начисленного платежа |
| 15 | Токен истек перед Save | Сессия обновляется; pending не теряется |
| 16 | Удален доступ клиенту | Старый snapshot/доступ больше не читается |
| 17 | Restore из дампа | Схема, строки, связи и business totals совпадают |
| 18 | Параллельный массовый импорт и ручное редактирование | Нет безусловного overwrite |

Текущие автотесты Mentori CRM дополнительно покрывают merge по записи/полю,
delete-vs-edit, append-only history, schedule по date, primitive sets,
pre-pull Save, in-flight Save, CAS race, микросекунды Postgres и pending recovery.

## 13. Порядок исправления другой CRM

1. Снять полный backup и доказать restore.
2. Найти и временно запретить все безусловные whole-state writers.
3. Ввести серверную version/CAS или row-level transactions.
4. Исправить pending: immutable snapshot, base, version, clear-after-success.
5. Добавить merge/retry либо перейти на per-row PATCH.
6. Перевести bot/webhook/cron на единый безопасный write service.
7. Добавить idempotency и SQL-транзакции денежным операциям.
8. Добавить audit log и actor attribution.
9. Настроить внешний автоматический backup и алерт ошибок.
10. Прогнать тест-матрицу локально и на staging.
11. Сделать staged deploy с возможностью быстро вернуть предыдущий release.
12. После deploy сверить counts/hashes и повторить реальный двухбраузерный smoke.

Не делать большой одновременный rewrite, если защиту можно вводить слоями. Но
нельзя оставлять хотя бы один старый writer, который обходит новый CAS: он снова
становится путем потери данных для всей системы.

## 14. Критерии приемки

Система считается готовой к одновременной работе только если:

- карта writers полная и подтверждена поиском по коду и runtime;
- нет безусловной полной перезаписи общих данных;
- все 18 сценариев имеют автоматическую или документированную live-проверку;
- конфликт не приводит к молчаливой потере локального или серверного значения;
- pending переживает reload/offline и очищается только после commit;
- платежи и другие многошаговые операции атомарны и идемпотентны;
- RLS и GRANT проверены реальными JWT каждой роли;
- backup хранится вне production host;
- restore реально выполнен и проверен;
- мониторинг замечает сбой записи, webhook, очереди и backup;
- отчет содержит оставшиеся риски, а не формулировку `все должно работать`.

## 17. Безопасное восстановление после инцидента

1. Остановить новые записи или включить maintenance mode.
2. Сохранить даже поврежденное текущее состояние отдельным backup-файлом.
3. Проверить browser pending на всех известных рабочих устройствах. Не удалять
   его, пока не экспортирован и не понятен его возраст/base version.
4. Найти последнюю целую версию по audit/history/payment records.
5. Восстановить ее в транзакции и выдать новую server version.
6. Пересобрать производные snapshots/read-models из источника истины.
7. Старый pending либо трехсторонне merge-ить, либо поместить в quarantine.
8. Сверить количества, финансы, заказы, связи и последние действия.
9. Только после проверки вернуть writers и обновить все открытые вкладки.

Нельзя просто восстановить сервер и попросить нажать reload: старая вкладка с
непроверенным pending способна повторно применить ошибочную версию.
